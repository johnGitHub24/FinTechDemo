FinTechDemo — 資料庫設計

教學介紹：本機 Demo 是兩個 H2

是的，本機 Demo 預設就是兩個資料庫（兩個獨立的 H2 記憶體庫），不是同一個 DB 裡只分表而已。risk、job、gateway 沒有自己的業務表。

兩個庫長什麼樣

服務 資料庫（本機） 主要表
order-service :8081 jdbc:h2:mem:fintechdemo users、orders、audit_log，還有 accounts、positions
account-service :8084 jdbc:h2:mem:accountdb accounts、positions
  • 表名 accounts／positions 在兩邊各有一份，但在不同服務、不同 H2 實例裡。
  • 兩邊沒有跨庫 FK，只靠 user_id 約定對齊（種子：1＝trader1、2＝admin）。

為什麼要這樣運作？

這是微服務拆邊界的 Demo 設計，不是 bug：

  1. 各服務管自己的資料 — order：登入／下單／審計；account：餘額／持倉（Portal 看的「正式帳本」）。
  2. order 裡仍有一份 accounts／positions（order 本機複本／standalone 帳本）— 只起 order 也能練成交；成交時 order 先改自己庫，再同步到 account。
  3. Portal 走 Gateway → account-service — 後台餘額／持倉讀的是 accountdb，不是 order 那份。

平常 Demo 成交（execute）怎麼跑？

  1. order 讀 order 庫 的 accounts → 送 risk 風控
  2. 風控過 → 改 order 庫 的 accounts／positions
  3. 再同步到 account-service（Feign apply-trade，或 Kafka trade-events）
  4. Portal 查餘額 → 讀 account 庫

若只改 order 庫、沒同步到 account，Portal 就會不同步（因此預設 fintech.account.feign-sync: true）。

flowchart LR subgraph ODB["order DB · fintechdemo"] U[users / orders] OA[accounts 本機複本] OP[positions 本機複本] end subgraph ADB["account DB · accountdb"] AA[accounts 正式] AP[positions 正式] end EX[order 成交 execute] --> OA EX --> OP EX -->|"Feign 或 Kafka"| AA EX --> AP Portal["Portal / 前台"] -->|Gateway| AA

一句話：兩個 H2、兩份帳本表名相同但不在同一庫；畫面看 account，成交先改 order 再同步。docker 可改 PostgreSQL，邊界不變。

用詞：order 本機複本＝order-service 內 H2 的 accounts／positions（成交內部用）；正式帳本＝account-service 的 accounts／positions（Portal 讀這裡）。舊稿偶爾寫「便道」，語意相同，已改為上述說法。

Demo 預設各服務獨立 H2（無跨庫 FK）。docker／demo 可改 PostgreSQL，邊界仍是「order 擁有訂單、account 擁有帳本」。
JPA 沒有 @ManyToOne：關聯全是邏輯 user_id／username。

H2 連線字串（本機 Demo）

兩張表所在的是兩個不同的 H2 記憶體庫（各服務各一個 JVM process）。服務關掉，該庫資料就沒了。共通帳密：username=sa、password=（空白）、driver=org.h2.Driver。

常見錯誤：在 DataGrip 對 order 填 jdbc:h2:mem:fintechdemo 會連到另一份空庫，不是正在跑的 order 進程。order 要用 TCP URL 或瀏覽器 :8081/h2-console。
參數：MODE=PostgreSQL＝SQL 方言靠近 Postgres；DB_CLOSE_DELAY=-1＝JVM 活著就保留 mem 資料。

ER Model — order DB（fintechdemo）

erDiagram USERS ||--|| ACCOUNTS : "owns user_id UK" USERS ||--o{ ORDERS : "places user_id" USERS ||--o{ POSITIONS : "holds user_id" USERS }o..o{ AUDIT_LOG : "username soft" USERS { bigint id PK varchar username UK varchar password_hash varchar role } ACCOUNTS { bigint id PK bigint user_id UK decimal cash_balance varchar currency } ORDERS { bigint id PK bigint user_id varchar client_order_id UK varchar symbol varchar side int quantity decimal price varchar status timestamp created_at timestamp updated_at } POSITIONS { bigint id PK bigint user_id varchar symbol int quantity decimal avg_price } AUDIT_LOG { bigint id PK varchar action varchar resource varchar detail varchar username timestamp created_at }

role＝USER／ADMIN；side＝BUY／SELL；status＝PENDING／ACCEPTED／REJECTED／CANCELLED。
accounts.user_id UNIQUE；positions(user_id,symbol) UNIQUE。
AUDIT_LOG 以 username 字串對齊 users.username（虛線＝非 DB FK）。此側 accounts／positions 是 standalone 帳本（order 本機複本）；正式帳本在 account DB。

ER Model — account DB（accountdb）

erDiagram ACC_ACCOUNTS { bigint id PK bigint user_id UK decimal cash_balance varchar currency } ACC_POSITIONS { bigint id PK bigint user_id varchar symbol int quantity decimal avg_price } ACC_ACCOUNTS ||--o{ ACC_POSITIONS : "same user_id"

表名實際仍是 accounts／positions（圖上加 ACC_ 前綴以免與 order 側混淆）。種子 user_id 1／2 對齊 order 的 trader1／admin，約定式對齊、無跨庫 FK。
