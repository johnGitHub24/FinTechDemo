第 5 章　雙庫與 ER Model

本機 Demo 預設是兩個 H2（不是同一 DB 分表）。欄位細節與 ER 圖權威： docs/architecture/db.html。

5.0 兩個資料庫，不是 bug

order-service 與 account-service 各有一個獨立的 H2 記憶體庫。risk、job、gateway 沒有業務表。

5.1 兩個庫長什麼樣

服務資料庫主要表
order :8081jdbc:h2:mem:fintechdemousers、orders、audit_log，還有 accounts、positions
account :8084jdbc:h2:mem:accountdbaccounts、positions
  • 表名 accounts／positions 兩邊各一份，但在不同 H2 實例
  • 無跨庫 FK；user_id 約定對齊（1＝trader1、2＝admin）

5.2 H2 連線字串（本機）

共通：username=sa、password=（空白）。服務關閉後 mem 庫即消失。

5.3 三種架構怎麼看

做法長相優點代價適合
單體 + 單 DB 一個 Spring Boot + 一個資料庫 最簡單；@Transactional 好處理；不太會有同步問題 模組容易耦合；邊界不明；不容易練分散式 CRUD 初學、功能先做出來
微服務 + 共用 DB 多個服務，但都連同一個 DB 比雙庫簡單；查詢方便；交易一致性較容易 服務容易互相偷讀 table；像拆了 API、沒拆資料 過渡期、團隊剛開始拆服務
微服務 + 各自 DB 每個服務管理自己的資料 邊界清楚；可各自部署；能練 Feign／Kafka／source of truth 最複雜；要處理同步、重試、最終一致性；跨服務查詢較麻煩 本專案現在這種教學型分散式架構
本專案的選擇：FinTechDemo 不是要走最省事的 CRUD，而是要練「服務拆開後，資料怎麼同步、畫面該信誰、Feign/Kafka 怎麼接」， 所以刻意採用 微服務 + 各自 DB。

5.4 初學者怎麼走比較順

  1. 先學 單體 + 單 DB：先把 CRUD、JPA、交易流程、@Transactional 搞懂。
  2. 再看 微服務 + 共用 DB：理解「API 雖然拆了，但資料其實還黏在一起」的過渡狀態。
  3. 最後練 微服務 + 各自 DB：開始面對同步、Feign、Kafka、source of truth、最終一致性。
白話：先學「一台店怎麼營業」，再學「分店怎麼分工」，最後才學「分店之間帳怎麼對」。 FinTechDemo 目前就是第三階段的練習。

5.6 為什麼要這樣？

  1. 微服務邊界 — order 管登入／訂單／審計；account 管餘額／持倉（Portal 正式帳本）
  2. order 本機複本（standalone 帳本）— 只起 order 也能練；成交先改 order 庫，再同步 account
  3. Portal — Gateway → account-service，讀 accountdb，不讀 order 那份

5.7 平常 Demo 成交怎麼跑？

  1. order 讀 order 庫 accounts → risk 風控
  2. 風控過 → 改 order 庫 accounts／positions
  3. Feign apply-trade 或 Kafka trade-events → 寫入 account 庫
  4. Portal 查餘額 → 讀 account 庫

只改 order、沒同步 → Portal 不同步（故預設 feign-sync: true）。

flowchart LR subgraph ODB["order DB · fintechdemo"] U[users / orders] OA[accounts 本機複本] OP[positions 本機複本] end subgraph ADB["account DB · accountdb"] AA[accounts 正式] AP[positions 正式] end EX[execute] --> OA EX --> OP EX -->|"Feign / Kafka"| AA EX --> AP Portal["Portal"] -->|Gateway| AA
一句話：兩個 H2、表名相同但不在同一庫；畫面看 account，成交先改 order 再同步。

第 6 章　分散式怎麼講

  • 微服務：三個業務服務拆邊界（不一定要 Eureka）
  • 同步：Feign 叫 risk；帳本可 Feign apply-trade
  • 非同步：Kafka topic 當 event bus（trade-events → account）
  • 快取：只有 account 讀路徑連 Redis；order／risk／gateway／job 本機預設不連。入帳後 evict
  • Eureka：可口述改 lb://，Demo 用固定 URL 保證可跑
  • 資料邊界：見 §5 ER — 訂單與帳本分庫，用事件／Feign 對齊
  • 排程：Job 不碰訂單表，只敲門；見 第 7 章

第 7 章　Job 逾時取消

一句話：Job 負責「時間到了去敲門」；真正把 PENDING 改成 CANCELLED 的是 order-service。 job-service 沒有 DB，不連 Redis。

7.1 系統流程

7.2 呼叫流程（看這張就好）

怎麼讀：箭頭都是實線、往下走＝一步做完再下一步。 中間的菱形是「token 對不對」：錯就 403 結束；對才進 Service 改資料庫。 （舊版時序圖裡的虛線＝HTTP 回傳，不是另一條業務路，容易誤會，已改成這張。）
flowchart TD A["1 Scheduler cron run"] --> B["2 job-service POST + X-Job-Token"] B --> C["3 InternalJobController cancel-stale"] C --> D{"4 token equals demo-job-token"} D -->|no| E["403 reject"] D -->|yes| F["5 StaleOrderService cancelStalePending"] F --> G["6 find PENDING over 30 min"] G --> H["7 set CANCELLED"] H --> I["8 return 200 cancelled = N"]
步驟誰做什麼
①～②job-service時間到了，帶 token 去敲門
③～④InternalJobController先驗 token；錯 → 403，對 → 往下
⑤～⑦StaleOrderService + orders真的改狀態
⑧Controller → job告訴 job 取消了幾筆

7.3 兩條觸發路徑（可只開 order）

誰觸發檔案何時用
本機 order 內建排程 order-service/.../StaleOrderCancelJob.java 只起 Order 也能掃逾時（LOOP 最短路徑）
獨立 job-service job-service/.../CancelStaleOrdersJob.java 示範「排程獨立部署」：HTTP 敲門，不共用 DB

兩邊 cron 都是 0 */1 * * * *（Spring 六欄）。同時開時可能掃兩次，第二次 cancelled=0，狀態不會錯。

7.4 設定與安全

項目值
逾時門檻fintech.job.stale-order-minutes: 30
內部密鑰X-Job-Token: demo-job-token（與 JWT 無關）
Security/api/internal/jobs/** permitAll，靠 token 擋外部誤打
Job 失敗order 沒起來時 job 只 warn，不讓排程執行緒掛掉

Case：STALE-001（單元＋整合）。檔案對照：SchedulingConfig、RemoteJobTriggerService、InternalJobController、StaleOrderService。

規範

第 10 章　SDD／TDD／Harness／Loop

完成的定義 = 閘門全綠，不是模型或口頭說 OK。長文權威：工程規範 · 部署關卡：Loop Engineering 教學。

一條鏈：規格 → 實作 → 閘門 → Demo

flowchart LR SPEC["SDD 規格與劇情"] --> TDD["TDD 單元加整合"] TDD --> APP["Vue 下單到 Order"] APP --> RISK["Feign 風控"] RISK --> ACC["帳務 Redis"] APP --> GATE["可選 Gateway Kafka"] TDD --> HARNESS["Harness check 閘門"] HARNESS --> LOOPOK["Loop until Demo ALL OK"]

實線主路徑：規格與測試先對齊，再走 Vue → Order → Feign 風控 → 帳務 Redis。Gateway／Kafka 是加分敘事。Harness 擋住壞變更後，Loop 把 Demo 拉到 ALL OK。

現場六步（務必可走完）

  1. 登入 trader1 / password
  2. /trade 下單
  3. Risk 成交（需 Risk :8082）
  4. /portal 看餘額／持倉／歷史
  5. admin 看 /portal/audit
  6. （加分）Gateway／Kafka／Redis

三個工具各當哪一道門

Harness 把「人工記得跑什麼」做成自動感測器 + 通過／不通過閘門。本專案三道門擋的「壞」不一樣。

工具它在擋什麼你實際的指令
hooks 改碼當下的「漂移」：例如只改單元測試、沒改整合測試 EngineeringOS scan-paired-tests.ps1、commit 前 lint
pipeline 這次變更能不能當「可部署的成品」 .\demo\verify-pipeline.ps1：gradlew check → docker compose config → K8s 清單
doctor 本機 Demo 現在能不能連（行程死了、埠空了） .\demo\doctor-demo.ps1；-Fix 再把缺的服務拉起來
flowchart TD CHANGE["code change"] HOOK["hooks: paired tests"] CHECK["check / pipeline"] DOCTOR["doctor: ports and health"] BLOCK{"all green"} NO["block: not done"] YES["pass this change"] CHANGE --> HOOK --> CHECK --> DOCTOR --> BLOCK BLOCK -->|red| NO BLOCK -->|green| YES
  • hooks：像煙霧偵測器，問題剛出現就叫。
  • pipeline：像出廠檢驗，測「這版能不能過 CI／能部署」。
  • doctor：像現場體檢，測「現在 localhost 能不能 Demo」。

pipeline 紅了，多半是程式或設定壞了；doctor 紅了，常常是服務沒開（關掉終端、重開機），不一定是邏輯寫錯。兩者都是閘門，擋的「壞」不一樣。
