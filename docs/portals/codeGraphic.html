技術次序與架構為什麼（md） 規格書 architecture 技術融合對照 從執行到 Entry Point

① 技術次序（你給的 Demo 堆疊）

  • 每個子專案解決「上一層做完後，下一個一定會被問到的問題」。
  • FinTechDemo 不是重做十個專案，而是把次序收成一條可演示鏈。
  • Demo 開場：先講這張次序圖，再講右邊系統如何對應。

對照 TradingSolution 路線：核心後端 → Gateway/MS → Kafka → 效能／維運 → 整合展示。FinTechDemo＝第⑥階段「一個倉庫講完」。

② 為什麼系統要這樣分層

  • Frontend：沒有 UI，展示只能 curl，故事弱。
  • Gateway：前端不該知道 order/risk 幾個埠 — Middleware 存在的理由。
  • MS + Kafka：拆服務解決邊界；Kafka 解決寫入尖峰 — 缺一就不是完整分散式敘事。
flowchart LR FE[Vue 前端] -->|為什麼：唯一 origin| GW[Spring Cloud Gateway] GW -->|為什麼：路由／聚合入口| MS[order / risk / job] MS -->|為什麼：寫入削峰| KF[Kafka] KF --> MS MS -->|為什麼：真相來源| DB[(PostgreSQL)] MS -->|為什麼：快取狀態| RD[(Redis)] MS -->|為什麼：橫切不污染業務| AUD[(audit_log)]

刻意不搬 Eureka／Config、Engine 多副本 Round-robin、R001–R010：次序要的是「形狀正確」，不是把練習倉全量貼上。

③ 請求主路徑（demo profile）

  • 查詢走同步 HTTP（列表／詳情要即時）。
  • 下單走 Kafka（可說明「入隊 ≠ 成交」；對齊 APIGatewayMQ）。
  • Risk 用 Feign 由 consumer／編排呼叫（對齊 MicroService）。
sequenceDiagram actor U as 使用者 participant V as Vue participant G as Gateway participant O as order-service participant K as Kafka participant R as risk-service participant P as PostgreSQL U->>V: 登入 / 下單 / 翻頁 V->>G: HTTPS /api/* G->>O: 路由（JWT FilterChain） U->>V: 下單 V->>G: POST /api/orders G->>O: 寫 PENDING O->>K: order-events O-->>V: 202 Accepted K->>O: consume O->>R: Feign 風控 R-->>O: OK / Reject O->>P: ACCEPTED + Position（AOP→audit_log） U->>V: 分頁列表 V->>G: GET /api/orders?page&size G->>O: 同步讀 DB O-->>V: PageResponse

local 可暫同步呼叫 risk（先過 P3）；docker/demo 必須走 Kafka，否則技術次序第 6 步在現場會講空。

④ 實作順序＝技術次序；最後才上雲

  • 先做 Paging／CRUD／JWT，才有「被 Gateway 保護與路由」的東西。
  • Gateway＋MS 同步打通後，再接 Kafka（你說的「Kafka 先不要」＝順序，不是刪除）。
  • Vue 接上後才做 Job／AOP／Prom／Locust／K8s — 證明層建立在可 Demo 鏈路上。
flowchart TB P1[P1 CRUD+分頁] --> P2[P2 JWT] P2 --> P3[P3 Gateway+Feign] P3 --> P4[P4 Kafka+Redis] P4 --> P5[P5 Vue 打通] P5 --> P6[P6 Job+AOP] P6 --> P7[P7 Actuator] P7 --> P8[P8 Locust] P8 --> P9[P9 Compose→K8s apps/clusters]

K8s 採 TradingKubernetes 最小結構：apps + infrastructure + clusters/{dev,staging,prod}；check 用 kustomize build，不強求本機真實叢集。
